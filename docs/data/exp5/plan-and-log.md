# OTW experiment 5: does retrieval work better when the same correction has been repeated? Plan fixed before evaluation (2026-10-28)

Observation from experiments 4 and 4b: each personal preference existed once in the store, so retrieval depended on one stored past-request sentence happening to resemble the new prompt (target found for 8/20 tasks by default, 11/20 without the similarity floor). OTW's premise is the opposite: the developer keeps repeating the same correction in different situations. With repeats there are several past requests per preference, so a lexical match has several chances.
Design change only in the store (nothing else is widened): the frozen exp2 store (150 records) plus 90 repeat records (3 per preference, written by Claude Opus 5.5 which saw only the 30 preference texts, never the tasks, prompts or code). Tasks, scorers, plugin, model, host unchanged.
Step A (offline, no model): family hit = at least one record of the target preference (original or repeat) among OTW's picks, for the 20 tasks, default floor vs no floor (cap 6). Reference: single-record store 8/20 and 11/20. Also quotes per prompt.
Step C (model, only if Step A improves): the 11 kept tasks of exp4, arms none, otw (default), otw_low (no floor), 3 fresh reps each (reps 10-12 of the fixture variants via rep numbers 1-3 reused; order shuffled, fixed seed), same runner with OTW_EXP_STORE pointing to the combined store. Reading fixed now: if default OTW passes clearly more with repeats than it did on the single-record store (8/33), then repeated corrections are where OTW pays; if otw_low is still better than otw, the opt-in stays recommended; if neither improves on the single-record store, retrieval of repeated preferences is not the lever.
Limits: synthetic repeats written by a model; 3 runs per cell; one small model; headless.

So repeats raise retrieval a lot even with the default floor (8 to 13 of 20), consistent with OTW's premise; the no-floor option adds more (17 of 20). Proceeding to Step C as planned: 11 kept tasks, arms none / otw / otw_low, 3 reps, order shuffled by a fixed seed.

## Log: experiment 5 result (99 runs, USD 0.43, every run produced a result)
Passes over 11 kept tasks x 3 reps: none 1/33, otw (default) 9/33, otw_low (no floor) 17/33. Sign tests across tasks: otw_low vs none 8 better / 0 worse / 3 tied, p = 0.008; otw vs none 5/0/6, p = 0.063; otw_low vs otw 3/0/8, p = 0.25. Pooled Fisher (runs not independent): otw vs none 0.013, otw_low vs none <0.001, otw_low vs otw 0.077.
Pre-stated reading applied: (1) default OTW with repeats passed 9/33 against 8/33 on the single-record store, so the better offline retrieval (family in block for 7 of 11 tasks instead of 4) did not turn into clearly more passes at the default floor; (2) the no-floor variant is again better (17/33 here, 16/33 vs 8/33 in 4b): replicated in two runs on two stores; (3) retrieval is not the only lever: tasks c004 and c006 stayed at 0/3 in every arm although the target family was in the block (3 target quotes in c006), i.e. the model sometimes does not follow a shown correction.
Pooled across 4b and 5 (different stores, independent runs): no floor 33/66 vs default 17/66. Mechanistic detail: passes by number of target-family quotes shown: 0 -> 3/15, 1 -> 14/33, 2 -> 6/6, 3+ -> 3/12; not monotonic (small numbers; c124 passed 3/3 with the floor off and 0/3 with it on although both showed 3 target quotes), so no claim that repeated quotes help beyond being found.

## Experiment 6 (harm check): does always showing 6 quotes hurt tasks where no preference applies? Plan fixed before running (2026-10-28)
The remaining cost of the wide setting is that every prompt gets 6 quotes, including prompts where nothing stored applies. The 14 exp2 tasks that the default model passed 3/3 with no recall are exactly the tasks where any harm would show as a lost pass. Arms: none (recall off) vs otw_low (no floor, 6 quotes; the exp2 store of 150 corrections as distractors), 3 fresh reps (4-6) per task, 14 tasks = 84 runs, order shuffled with a fixed seed. Harm is declared if the pooled pass rate with otw_low is lower than none by 10 points or more, or if 3 or more tasks lose 2 or more of 3 passes. Also reported: mean turns, output tokens and seconds. A "no harm" reading means not detected at this size, not proven.
